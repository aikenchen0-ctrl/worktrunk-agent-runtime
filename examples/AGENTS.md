# AAR Agent 协作规则

这是业务仓库接入模板：合并到适用的 AGENTS.md，不覆盖既有规则。详细流程由三个 Skill 按需加载。本文件不授予远端发布、推送、建 PR、跨任务消息或合并权限。

## 身份、目录与隔离

1. 开始时确认本任务拥有的仓库、Worktree、分支、模块、消费者唯一标识、Gradle 项目和变体。只修改自己拥有的目录；不重置、stash 或覆盖其他任务的未提交工作。
2. 从现有项目登记定位接口说明、迁移文档、依赖图和候选路由；缺失项先列出，不假定示例中的文件或模块已经存在。新增 AAR 时先登记模块、消费者、构建入口及根构建文件负责人。
3. 使用稳定唯一的 AGENT_ID，所有参与者和 Worktrunk Hook 共享同一个已登记的短 AGENT_RUNTIME_ROOT。每个 Worktree 保留自己的可写缓存和构建输出；不要在构建中切换状态根或共用写目录。
4. 先核对实际 agentctl 版本及配套脚本，再执行 prepare、doctor。Gradle 构建与发布走 run-gradle，ADB 操作走受控入口；不存在的命令不得猜测。
5. 默认独立下载依赖；快照仅作为明确选择的优化，导入空私有缓存。新依赖在当前私有缓存验证，种子维护者生成新快照，不修改旧快照或复制正在写入的缓存。

## 何时检查变化

- 在开始或恢复任务、当前构建结束、正式验证或推送前，以及交付前，检查当前消费者的 event-inbox 与实际验证状态。
- 不逐条聊天轮询，不等待全部模块一起完成，不在正在运行的构建中切换依赖。候选先进入待评估列表，只在明确采用时改变固定组合。
- 同机独立仓库收到原始事件文件后按协议 event-import；不要把收件箱输出当原始事件。跨机器身份不匹配时报告，不改写事件中的路径。
- 只有本消费者核对并首次接收的事件才确认 received；已有验证状态不能退回 received。消息送达、已接收、已迁移、通过、合并分别记录。

## 按任务使用 Skill

- 契约修改、草稿预告、候选构建/发布及发布中断恢复：aar-candidate。
- 固定候选迁移、消费者验证、升级草稿 PR 及其恢复：aar-upgrade。
- 消费者汇总、获准的定向通知、一轮协调与集成前检查：aar-coordinate。
- Skill 或工具不可用时输出具体交接和阻塞，不声称已经投递、创建 PR 或后台调度。已有授权覆盖的动作可以连续执行；新增外部目标另行确认。

## 契约和候选

1. API 允许变化。接口与迁移说明由提供方在自己的仓库版本化保存；只有契约变化才更新，不让十几个 Agent 同写一份实时接口文档。
2. 对实际模块用 contract-snapshot、contract-diff 比较同范围已发布基线；扫描不是完整 ABI 或行为证明。补查资源、Manifest、序列化、线程、错误语义、JNI 和传递依赖。首次无基线时兼容性未知。
3. 破坏性差异应触发迁移计划而不是禁止开发。需要提前协作时发草稿预告，允许明确标记的桩或适配层；正式确认必须改用真实制品重验。
4. 正式候选来自干净、确定的提交，直接采用 candidate-version 输出的版本；固定坐标，不共享 mavenLocal()、不使用动态版本或 SNAPSHOT。远端不可覆盖由已有服务保障，不以提示词或先查后传代替。
5. 制品及必要元数据完整可读、摘要核对后才创建 contract-event；使用明确消费者路由，不能仅用 :app 区分仓库。发布后得到的事件与摘要放到外部交接记录，不为写入这些信息更改已发布源码提交。
6. 发布、事件生成、通知失败分别恢复：先查实际结果，不重复覆盖制品、不重新造事件、不把未知发送结果当成失败后盲目重发。

## 迁移、验证与合并

1. 稳定分支继续固定旧版本；升级在本任务拥有的迁移分支进行。读取真实版本目录、锁文件和解析图，只改本工作项候选；不能同时解析同模块旧 project(...) 与新 Maven 制品。
2. 正式消费者验证前提交获准迁移并保持工作区干净，调用配套 validate-candidate.ps1，核对真实版本属性、项目、解析配置与 JVM 测试任务。help、assemble、零测试、旧报告不能确认 passed。
3. 活动验证租约按控制器规则处理，不删除未知锁；只有实际验证工具能产生绑定事件、提交、制品和本次尝试的成功收据。
4. 推送或建 PR 前核对工作项归属、目标仓库/分支与授权；查询已有所有状态的 PR。指定单一执行者或使用已有原子认领，不把先查询视为锁。重试复用原工作项，不强推、不擅自重开或自动合并。
5. 多仓源码分别合并，以固定制品组合集成。同仓 settings、根构建文件、版本目录等共享文件按现有负责人或合并队列处理。rebase、冲突解决、基准分支变化或候选变化后重新核对测试；旧头提交的 CI 不证明当前变更通过。
6. 集成 Agent 在自己的 Worktree 固定清单并运行 run-integration。消费者未齐时仅可显式探索 --allow-pending-consumers；通过也不能填补缺失收据。分别报告 combination_verified、ready_for_integration 和 release_approved，禁止篡改原值。

## 交接与完成

- 提供方交接：草稿/就绪阶段、仓库/模块/完整提交、接口差异与迁移、精确坐标及摘要、原始事件、已知消费者和未知影响。
- 消费者交接：采用的固定组合、迁移提交、真实测试与收据、PR/CI 头提交、未通过项和下一责任方。
- 协调者记录：已核实任务映射、用户授权来源、投递结果、消费者与组合证据。无消息工具时保存待发送内容；不编辑 Desktop 私有数据库、不创建未获准定时任务。
- 交接使用 Skill 自带模板或项目既有同类格式。每个工作项的拥有者维护自己的记录，协调者只汇总；文档不是锁、权威收据或授权令牌。
- 自动调用时分开 stdout JSON 与 stderr 日志，检查退出码及错误含义。dependency-audit --enforce 是辅助检查，不替代真实解析与测试。
- 最终报告分别说明本地验证、远端发布、消息投递、消费者迁移、PR 和集成结果；只报告真实完成项，不把一项成功推导为全部通过。
