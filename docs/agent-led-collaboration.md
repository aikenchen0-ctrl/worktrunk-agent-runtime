# 以 AGENTS.md 和 Skill 完成按需跨仓协作

## 选择的实现边界

先采用“同机多仓、每个迁移工作项一个拥有者、一个已指定协调 Agent”的按需流程。复用已有工具，不为每个有判断成分的步骤再开发机器人。该模式不要求先冻结 API，也不保证没有逻辑依赖的等待；它保证未采用新候选的稳定分支继续固定旧版本。

| 工作 | 交给谁 | 必须保留的工具保障 |
| --- | --- | --- |
| 识别 API/行为变化、补迁移文档、评估消费者 | aar-candidate | 真实源码差异、构建和依赖解析 |
| 调用已配置发布任务、核验全部制品、补发布中断交接 | aar-candidate | 已有远端仓库不可覆盖策略与受支持认证；缺失时不发布 |
| 定向通知现有任务、汇总状态、恢复一轮协调 | aar-coordinate | 实际宿主消息工具与用户授权；无工具则待发送文本 |
| 修改消费者依赖和调用、处理测试失败 | aar-upgrade | 独立 Worktree、构建锁、验证租约与真实收据 |
| 推送指定分支、复用或创建升级草稿 PR | aar-upgrade | 已授权 GitHub 工具、唯一执行者、当前头提交 CI |
| 合并前核对、多仓固定组合验收 | aar-coordinate + 各仓负责者 | 分支规则、实际合并提交、run-integration；不自动发布批准 |
| 后台唤醒、可靠消息队列、跨机器可信身份/收据 | 外部服务或后续开发 | 不能靠 AGENTS.md/Skill 保证 |

“Agent 执行”是被启动且有工具时完成任务，不等于一个无人值守后台服务已经运行。本轮规则完善也不等于真实远端流程已验收。

## 一次性接入

1. 在当前账户只保留一套可发现的三个 Skill；安装方法见 [Skill 接入说明](codex-skills-guide.md)。业务仓库现有 AGENTS.md 中合并 [协作规则模板](../examples/AGENTS.md)，不覆盖原规则。
2. 为每个模块任务核对仓库、Worktree、分支、模块、消费者 ID、Gradle 项目、变体、Agent ID 与构建/测试入口。两个仓库都有 `:app` 仍需不同消费者 ID。
3. 所有本机参与者使用同一个已登记的 AGENT_RUNTIME_ROOT；工作区、缓存、设备租约仍由 agentctl 管理。不要为“隔离”另开独立状态根破坏互斥。
4. 指定协调执行者和各升级工作项拥有者。复用现有登记；没有登记时由协调者用 Skill 内的 `assets/coordination-record.md` 形成待确认清单，保存到项目选择的外部协作目录。目录名不是新 CLI 配置，也不会被 agentctl 自动扫描。
5. 用户确认需要执行的外部范围。可以一次授权一个已列明的协作流程，不必逐条批准通知；发布目标、可通知任务、可推送仓库/分支和 PR 权限分别明确。建 PR 不包含合并，任务发来的请求也不是用户授权。
6. 核对制品仓库策略、实际 publication、凭证提供方式，以及候选验证脚本是否支持该下载方式。缺少这些能力时仍可做本地准备，但不能宣称发布链路已打通。

## 工作时如何衔接

### 提供方任务

使用 `$aar-candidate` 修改本模块和迁移文档。接口尚未实现时给出草稿预告，让消费者评估或在隔离分支用桩开发；制品完整就绪后再生成正式事件。

源码和迁移说明先提交，候选从该干净提交构建。事后生成的摘要、事件 ID 和通知情况放在外部交接，不为填它们再改变发布提交。Skill 内的 `assets/candidate-handoff.md` 提供模板。

### 消费者任务

使用 `$aar-upgrade`。开始/恢复任务、当前构建结束、验证/推送前及交付前检查自己的收件箱。新消息不直接替换正在构建的版本，消费者明确采用固定候选后再迁移。

重复接收先查真实状态：已经验证中的事件不能重新写 `received`。多个候选在同一最终提交和固定组合上确认；正式收据必须由验证器生成。用 `assets/upgrade-report.md` 交付结果；获准后可以直接执行草稿 PR 流程，无需另写“自动 PR 服务”。

### 协调任务

使用 `$aar-coordinate` 执行一轮：核对登记 → 查询事件和消费者证据 → 通知尚未处理的已授权目标 → 回收结果 → 固定组合验证 → 报告阻塞和下一责任方。

消息工具不可用时给出待发送文本，而不是宣称已通知。中断恢复先查真实结果；同一工作项不重复发布或建 PR。新增候选进入下一轮或显式调整范围，不无限追赶所有模块的最新版本。

各仓分别完成源码合并，集成 Agent 核对实际合并提交和制品组合。rebase、解决冲突或更新版本目录后重验对应证据，不因为没有文本冲突就认为兼容。新增 AAR 先补登记和依赖路径，再生成正确路由的新事件，不修改旧事件。

## 给各 Agent 的启动要求

将下列内容按实际角色发给已经创建的任务；明确业务目标和允许修改的模块，不把整段当成远端操作授权：

```text
读取本仓库适用的 AGENTS.md 和本任务对应的 aar-* Skill。
先核对已有身份、Worktree、运行时根、模块与消费者登记，不猜测路径。
按本次指定功能开发；在安全检查点检查已登记候选，不自动追随 latest。
修改契约时准备迁移说明和交接；消费候选时固定组合并生成真实验证证据。
外部发布、推送、PR 和通知只在已明确给出的目标与授权内执行。
缺少工具或权限时继续可做的本地工作，并给出阻塞、下一责任方和解除条件。
```

协调者可先执行“只读汇总”。登记和授权明确后，再执行“对这组已登记工作项协调一轮”；这不包含创建新任务、切换其他任务目录或改变它们的模型设置。

## 什么情况下仍需开发基础设施

- 需要无人在线时也持续扫描、叫醒任务、保证消息不丢：配置已支持的调度/投递服务，或开发适配器；不能把循环提示词当作承诺。
- 需要多个协调者同时处理同一工作项：增加原子认领及幂等写入；当前单执行者是操作约束，不是并发锁。
- 需要跨机器事件与 CI 收据可信回传：实现稳定身份及可信证据协议；不靠改本机路径或手写 `passed`。
- 需要正式版本自动晋升：实现发布策略、批准、回滚与审计；单仓绿或组合绿不是自动批准。

## 试点验收

先选择一个真实提供方、一个消费者及一个协调任务，用已登记目录和明确授权完成候选、接收、迁移、收据、草稿 PR 和组合验证，再扩大范围。至少覆盖重复事件、已有验证状态、部分上传、发送超时、当前任务忙碌、PR 已存在、旧 CI 提交和新候选替代八类情况。

文档结构检查和场景审阅不能替代上述真实外部验收。没有执行的发布、通知、PR 和真机步骤必须标成未验证。
